What Epic's front ends are actually built from

Three properties, one component library. This is a measured study of the colour tokens, type scales and components behind Unreal Engine, the Epic Games Store and Fortnite for Developers — the names the systems use for themselves, the values the browser computes, the CSS that recreates each entry, and the rules for using it. Everything here was read off the live pages in a real browser, not copied from a brand guide.

Collected 16 November 2026 · headless Chrome 157 at 1440×1000 and 390×1000 CSS px · 4,041 rendered elements inspected across the three pages · 2,668 + 2,258 published custom properties read · 61 remote asset URLs checked, 42 of them confirmed loaded by the browser.

1 · How this was collected

The three pages were loaded in headless Chrome, allowed to hydrate, and then read through the DOM and the CSSOM. Nothing was inferred from screenshots alone and nothing was taken from documentation: every value below is either a declaration found on a live stylesheet or a getComputedStyle result on a rendered element. The scraper that does this is tools/design-library-scrape.mjs, and the raw dumps it produced are in support/library-data/.

What was measured

  • Declarations — every custom property on every readable stylesheet, with the selector that declares it, so a token can be attributed to :root or to one component's class.
  • Computed styles — font family, size, weight, line-height, letter-spacing and text-transform for headings, body copy, links, buttons and inputs; colour, background, border, radius, padding and shadow for every rendered element, tallied by frequency.
  • Components — button, input, card and navigation treatments grouped by their full computed signature, so two buttons are "the same button" only if every property matches.
  • Assets — favicons, manifests, social images, @font-face files, inline SVG marks and CSS-drawn art, each then re-requested to confirm it resolves.
  • The composed tree — shadow roots included. This turned out to matter more than anything else in the study; see §2.

Known limits, stated plainly

  • This is a derived study, not an Epic Games brand kit. Trademarks, logos and typefaces belong to Epic Games. The names in §3.1 and the CSS in §2.2 are quoted from public stylesheets for reference and comparison; treat hotlinked assets in §6 as reference material, not as licensed production dependencies.
  • OneTrust was excluded. All three sites load the same OneTrust consent overlay, which injects its own palette and type (12.25px headings, #555 text, its own buttons). It appears in every page's DOM and would have contaminated the census; its nodes are filtered out by id and class.
  • Two viewports, not a matrix. The type tables give 1440px and 390px values. Two of the three sites derive some sizes fluidly, so intermediate widths sit between the two columns; Fortnite's fluid sizes are reported as the fractional pixels the browser computed.
  • Page-specific chrome is labelled as such. Where a value comes from one property's own page layout rather than the shared library — the store's 100px department bar, the Fortnite sub-nav — the entry says so.
  • Bot-walled files. Files served from www.unrealengine.com, store.epicgames.com and www.fortnite.com answer a scripted request with 403 while loading normally in a browser. Those URLs were verified from inside the page instead, and are marked in §6.

2 · The shared layer

The headline finding is structural. The header on all three sites is the same web component, shipped from components.unrealengine.com and mounted under a different tag name on each property: <unrealengine-navigation>, <egs-navigation>, <fortnite-navigation>. Each renders its contents inside a shadow root, which is why a conventional scrape of the page — including the one this document started from — sees a header-sized gap and an unstyled nav.

Inside the shadow root the structure is identical, and so are the custom properties the component declares. The component is themed from outside by those properties, and each property passes in its own accent: the Fortnite page sets --color-fill-primary-default: #f7ff19 on the host and the same component turns yellow.

The pattern worth stealing

The component's own breakpoints are narrower and more numerous than a marketing site usually needs. The primary mobile boundary is 720px:

Focus ring

Focus is a white 2px outline with a 2px offset and a tightened radius, on every interactive element across all three properties:

Motion

Two durations carry the whole system: .12s for state changes on colour, background and border, and .3s for the brand mark's transform and width as the header reflows. Both use the same curve. The store publishes the same idea as tokens — see §3.1.

3 · Colour

There are two colour systems in play, and it is worth keeping them apart. The Epic Games Store publishes a complete, named token architecture on :root — 784 root-level custom properties out of 2,668 on the page. Unreal Engine and Fortnite for Developers publish almost nothing by name: their variables are compiler-generated hashes (--ue0mn5, --_1m8v6gs0), so their palettes have to be read off computed styles. §3.1 is therefore quoted, and §3.2 is derived and labelled as such.

3.1 The published token system

The store's system is three layers deep and entirely mechanical, which is what makes it usable: a raw palette of twelve hues at seven steps each, a neutral ramp, then semantic names that describe a job rather than a colour, then component slots built from the semantics. Nothing consumes a palette step directly except the semantic layer.

The shadows are the most interesting entry here. Instead of one blurred shadow, each direction is a five-step ramp whose blur and offset double at every layer, all at 10% black. The shared header uses exactly this construction for the drawer.

3.4 Rules of use

  • One accent per property, chosen at the top. Cyan on Unreal Engine, a brighter cyan on the store, yellow on Fortnite. The shared component reads the accent from a single custom property, so the accent is never hard-coded in a component.
  • Depth is alpha, not new greys. Rest, hover and pressed states are 5% → 15% → 35% white fills on the canvas. The store's token names encode this directly (faint, subdued, subtle, strong).
  • Fills lighten on hover; they do not swap colour. Both the store's tokens and the shared header move from a 15% fill to a 35% fill. Nothing in the census changes hue on hover.
  • Cards use near-invisible borders. Unreal Engine's card border is the same 5% white as its fill; the store's is 15% white on a #14181E card. A visible border on a dark canvas reads as a box, not a surface.
  • Text is white at four strengths, never four greys. 100%, 95%, 75–65%, and a muted grey for genuinely tertiary content.
  • Status colours come in pairs. A bright fill for the surface plus a dark tint of the same hue for the label — never black on colour.
  • Scrims are 35% and 65% black (#00000059, #000000a6), not a blur, when content must stay legible behind an overlay.

4.3 Rules of use

  • Tracking moves opposite to size. Big type loses letterspace (-0.035em at 64px), small type gains it (+0.04em at 10px). This is the single most reproducible rule in the study, and the only one the store bothered to publish per step.
  • Line-height follows role, not size. Display ≈ 1.2 (or 0.99 in the poster-like Fortnite case), headings 1.2, body 1.65–1.73, UI text 1.3–1.5.
  • Only display sizes scale with the viewport. Buttons stay 14px and nav links stay 16px at both 1440px and 390px on all three sites. Body copy may step down one notch (16 → 14px) at the mobile breakpoint.
  • Two weights per family is enough. 400 and 500/700. The 900 weight is declared everywhere and used nowhere on these pages; the variable faces use 300 / 650 / 750 to hit intermediate weights instead of loading a second file.
  • Sentence case by default. The only exceptions are Fortnite's display headings, which are uppercased with text-transform so the copy underneath stays readable and searchable, and the small labels that are genuinely labels ("STEP 1").
  • No italics except as voice. The only italic in the entire study is Fortnite's display face, where the slanted variable cut is the brand.
  • Text is never pure white on these pages except for headings. Body copy sits at 95% or 65% white; the store's token default is #fffffff2.
  • Set font: inherit on form controls. The one place the system visibly breaks is an input that inherited the browser's default font (see §4.1).

Usage spec

  • One primary per view. Every page in the study has exactly one filled accent button in its hero or toolbar.
  • The accent is a variable, never a literal. The same component renders cyan on Unreal Engine and yellow on Fortnite because only the variable changes.
  • Pick the height from the scale, not the content. 24px (tag) → 32px (tile) → 40px (standard, and the most common) → 44px (hero on Fortnite) → 48px (store hero).
  • Radius is property identity. Unreal Engine 8px, store 8–10px, Fortnite 6px. A pill (9999px) is reserved for tags, filters and step chips, never for an action.
  • Label type differs by brand and is not negotiable. Unreal Engine and the store use 14px/500 with +0.02em tracking; Fortnite uses 16px/400 with no tracking because its display face is already heavy.
  • Hover strengthens a fill or a border; it never moves the button. No lift, no scale, no shadow appearing on hover anywhere in the three sites' rest states.
  • Disabled is 50% opacity plus a pointer-events guard — the fill is not swapped for grey.
  • Icon-only buttons keep a 24px glyph in a 32px target, and the glyph inherits currentColor so it themes with its container.

5.7 The ambient image glow

This is the effect that makes the art on an inner page look like it is lighting the canvas around it: a soft, saturated haze of the image's own colours bleeding roughly 160px past its edges. It appears on Unreal Engine's inner pages — /features is the clearest example — and it is the most sophisticated thing in this study.

It is not a CSS filter: blur() on a copy of the image. The blurred copy is painted into a canvas one eighth of the size and then stretched back up by CSS, so the browser's own bilinear magnification does the blurring at a sixty-fourth of the pixel cost.

What is actually in the DOM, measured

div.image-holder                      643×362   position: relative

│   │                                   the SAME art, from a 256px-wide CMS variant
│   └── canvas.blurred-image__canvas  intrinsic 120×85, laid out 963×682
│                                       aria-hidden="true"; position: absolute; inset: 0; width/height 100%
└── img.cosmos-asset                  643×362   z-index: 2; border-radius: 24px   ← the card itself

Read those two numbers together: 963 ÷ 120 = 8.02 and 682 ÷ 85 = 8.02. The canvas holds 10,200 pixels where the box it fills has 656,000 — and the 8× magnification is the blur. The wrapper is sized inset: calc(var(--image-blur-pixels) * -2), so the aura's reach is always exactly twice the blur radius; here that resolved to −160px, meaning the component was given an 80px radius on this page (its own default is 50px, and its CSS fallback is 125px).

The pipeline, in the order it runs

  1. A hidden duplicate of the art. Not the hero file: image.optUrl || resize({ src: image.url, width: 256 }) — a 256px-wide transform of the same CMS asset, loaded crossOrigin="anonymous" so it can be uploaded as a WebGL texture without tainting the canvas, and marked aria-hidden as decoration.
  2. A shared offscreen WebGL canvas, 300×150 (the browser default — its size is never set), reused across instances. The image is uploaded as a texture.
  3. A two-pass separable Gaussian blur in GLSL: a horizontal pass into framebuffer A with u_blurRadius, then a vertical pass into framebuffer B. Measured radius: u_blurRadius = 10 — the 80px radius divided by the 8× downsample, because the blur is computed at the small resolution.
  4. A composite pass with u_saturation (measured 1 — the aura keeps the art's true colour) and u_distortion (measured 1 — a slow wobble, forced to 0 under prefers-reduced-motion).
  5. One drawImage that copies a band, not the whole buffer — drawImage(gl, 0, gl.height - n, w, n, 0, 0, w, n). Measured live as drawImage(canvas, 0, 65, 120, 85, 0, 0, 120, 85): the WebGL result lands in the bottom 85 rows of the 150-tall GL canvas (WebGL's origin is bottom-left), so the copy takes that band. This step is what explains the odd-looking numbers.
  6. CSS stretches the 120×85 canvas to 963×682 — position: absolute; inset: 0; width: 100%; height: 100% — and the smoothing filter turns 10,200 pixels into a 160px-wide glow.
  7. It redraws at 30fps (1000 / 30): 414 draws measured over 13.7 seconds. The loop exists for the animation, not the blur — the wobble needs a new frame, and each frame is cheap precisely because the buffer is tiny.

Recreating it without WebGL

The structure is the whole trick; the shader is an optimisation. This is the same effect in portable CSS — a copy of the art, inset by twice the blur radius, behind the content and inert to the pointer. 

/* 1 · the card and its aura share a positioned parent */
.glow { position: relative; }

/* 2 · the aura layer: bleeds twice the blur radius past the content on every side */
.glow__aura {
  position: absolute;
  inset: calc(var(--glow-blur, 50px) * -2);   /* 80px radius → 160px of reach */
  z-index: 0;
  pointer-events: none;                       /* never intercept a click or a hover */
}

/* 3 · the blurred copy — either let CSS blur it… */
.glow__aura img {
  display: block; width: 100%; height: 100%;
  object-fit: cover;                          /* fill the aura box, crop the overflow */
  filter: blur(var(--glow-blur, 50px)) saturate(1);
  opacity: var(--glow-opacity, 1);
}

/* …or do what Epic does and upscale a tiny canvas instead (far cheaper, and it can animate) */
.glow__aura canvas { display: block; width: 100%; height: 100%; }

/* 4 · the content rides above the aura */
.glow__card { position: relative; z-index: 2; border-radius: 24px; overflow: hidden; }
/* The cheap version: paint the art into a canvas 1/8 of the box and let CSS magnify it.
   Same technique, no shader, ~20 lines — and it works with an ordinary <img>. */
const DOWNSAMPLE = 8;

function paintGlow(canvas, img) {
  const rect = canvas.getBoundingClientRect();
  canvas.width = Math.max(1, Math.round(rect.width / DOWNSAMPLE));
  canvas.height = Math.max(1, Math.round(rect.height / DOWNSAMPLE));
  const ctx = canvas.getContext("2d");

  /* cover-fit the source, the way object-fit: cover would */
  const scale = Math.max(canvas.width / img.naturalWidth, canvas.height / img.naturalHeight);
  const w = img.naturalWidth * scale;
  const h = img.naturalHeight * scale;
  ctx.drawImage(img, (canvas.width - w) / 2, (canvas.height - h) / 2, w, h);
  /* no ctx.filter, no blur — the browser's own upscaling is the blur */
}

const canvas = document.querySelector(".glow__aura canvas");
const img = document.querySelector(".glow__aura img");
img.decode().then(() => paintGlow(canvas, img));
new ResizeObserver(() => paintGlow(canvas, img)).observe(canvas);

Two conveniences in the original are worth copying ahead of the shader: the hidden source is a 256px-wide transform of the artwork — a blur destroys detail, so never download the full-size file for it — and the aura is pointer-events: none, so the card underneath stays fully interactive.

Usage spec

  • Only when the art has colour to give. The effect reads as the image emitting light, so it needs a saturated or high-contrast picture — a grey screenshot produces a grey smudge.
  • Reach is always twice the blur radius (inset: calc(var(--blur) * -2)). More and the haze stops belonging to the image; less and it looks like a rendering artefact.
  • One glow per view, on the hero. It is the loudest owner of the background in the whole study, and it is used on inner-page heroes — not on cards in a grid.
  • The aura never carries meaning. It is aria-hidden, ignores the pointer, sits at z-index: 0 under a card at z-index: 2, and no text sits on it, so contrast is untouched.
  • Keep the blur cheap: downsample the canvas (8× here), blur a small asset, reuse one GL context across instances, and cap the redraw rate if it animates at all.
  • Turn the motion off, not the glow, under prefers-reduced-motion — the distortion goes to zero and the aura holds still.
  • Watch the box. An element extending 160px past its parent can add scrollbars near a viewport edge; clamp the aura's parent with overflow: hidden, or drop the effect on small screens, where the reach would outrun the margin anyway.
Why it looks like it belongs to the image

Because it is the image — the same pixels, low-passed until only the colour field survives. That is why a small CMS transform is enough, why the aura follows the artwork's real palette (red neon on the left, green on the right in the example), and why it never reads as a decorative gradient bolted on: there is no hue in the glow that is not in the picture.

8 · Method, files, reproduction

What was run

  • node tools/design-library-scrape.mjs — launches headless Chrome, loads each site, waits for hydration, reads the composed tree (shadow roots included), then re-measures at 390px and probes same-origin assets.
  • Four scrapes were taken. The first three were discarded for cause, and the reasons are recorded because they are the kind of error this kind of study invites: the consent overlay's palette and type leaking into the census, and the shared header being invisible to querySelectorAll because it lives in a shadow root.
  • 61 candidate asset URLs were then re-requested: 42 confirmed loaded by the browser, 18 that the page never requested (favicons and unused weights), 1 that failed.

Files

  • support/library-data/<site>.json — the raw dump per site: 2,668 + 2,258 + 1 custom properties, the colour and type censuses, component groups, asset inventory, the browser network log, the same-origin probe and both viewport measurements.
  • support/library-data/<site>-navigation.css — the shared navigation component's own stylesheet, captured verbatim from its shadow root, ~39KB each.
  • tools/design-library-scrape.mjs — the scraper, documented at the top of the file.
  • support/library.html — this document.

To reproduce

node tools/design-library-scrape.mjs            # all three sites, ~2.5 minutes
node tools/design-library-scrape.mjs fortnite-developer   # one site

What this pass did not capture

  • Footer internals. Both footers are shared web components (<unrealengine-footer>, <egs-footer>, <fortnite-footer>); only their mounting was recorded.
  • The nested search box. <epic-wf-search-box> is not in the DOM until the search is opened, so its internals are undocumented here.
  • Rendered hover, press and focus states. The state values come from the tokens and declared rules, not from driving the page. Everything quoted is evidence; nothing about a hover animation is claimed.
  • The store's grid, carousel and product-page components. This pass covers the landing pages of three properties, which is where the shared system is visible; a product page would add its own vocabulary.
  • Anything behind a login. The account dropdown and wallet elements were seen only as declared markup and closed state.
